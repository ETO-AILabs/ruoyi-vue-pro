# 自动头像方案说明

## 1. 背景

当前项目包含两类头像相关逻辑：

1. 会员用户头像，存储在 `member_user.avatar`
2. 分身/社交头像，创建分身时由后端随机分配，前端部分页面在无头像时使用本地静态图兜底

本次排查的目标是确认：

- 当前头像从哪里来
- 为什么数据库里存在 `https://i.pravatar.cc/300?img=xx`
- `member_avatars` 是否还在生效
- 后续如果要做随机头像，应该怎么落地
- 头像资源应该上传到哪里、怎么配置存储

---

## 2. 当前结论

### 2.1 `member_avatars` 表当前为空

已确认线上数据库 `eto_database.member_avatars` 当前无数据。

查询 SQL：

```sql
SELECT COUNT(*) AS total_avatar_pool, COUNT(DISTINCT image_url) AS distinct_pool_urls
FROM member_avatars;
```

查询结果：

```text
total_avatar_pool = 0
distinct_pool_urls = 0
```

这意味着：

- 当前后端正式的“随机头像池”已经失效
- 创建分身时如果继续走随机分配逻辑，将无法从 `member_avatars` 中取到头像

### 2.2 `member_user.avatar` 中存在多种来源

当前数据库中的 `member_user.avatar` 主要来源包括：

- `i.pravatar.cc`
- `thirdwx.qlogo.cn`
- `test.yudao.iocoder.cn`
- 其它外部 URL
- 少量空值

说明当前数据库里的头像并不是统一来源，而是历史过程中由多条链路写入。

### 2.3 前端存在本地默认头像兜底

`yudao-mall-uniapp` 中部分页面在没有头像时，会直接使用本地静态图：

- `/static/style_3d.jpg`

这张图不是数据库中的头像，也不是后端随机生成的头像，而是前端本地资源兜底图。

因此即使数据库头像失效，部分页面仍然可能显示正常。

---

## 3. 当前代码链路

### 3.1 分身创建时的头像来源

前端创建分身时调用：

- `POST /member/user/clone`

对应前端代码：

- `yudao-mall-uniapp/sheep/api/agent/profile.js`

当前前端创建分身时并不会自己上传头像，而是把头像分配交给后端。

后端代码位于：

- `AppMemberUserController`
- `MemberUserServiceImpl`
- `AvatarServiceImpl`

核心逻辑如下：

1. `createClone()` 执行创建分身
2. 后端调用 `avatarService.getRandomAvatar()`
3. `AvatarServiceImpl` 从 `member_avatars` 表中查出所有头像
4. 随机取一条
5. 将该条记录的 `image_url` 写入 `member_user.avatar`

所以，当前正式设计的分身头像方案本质上是：

**头像池随机分配**

不是实时 AI 生成，也不是前端传头像。

### 3.2 `/member/user/avatar/random` 的作用

后端还提供了接口：

- `GET /member/user/avatar/random`

这个接口同样是：

1. 从 `member_avatars` 随机取一条
2. 更新当前用户的 `member_user.avatar`
3. 返回新的头像 URL

不过根据前端代码检查，当前 uniapp 项目虽然封装了该接口，但并未真正调用。

因此当前实际主流程仍然是：

- 创建分身时由后端随机分配头像

### 3.3 普通会员头像的另一条来源

除分身创建外，普通会员还可能通过微信授权获取头像。

uniapp 中的逻辑是：

1. 小程序授权返回微信头像临时地址
2. 前端调用 `/infra/file/upload` 上传图片
3. 上传成功后，将返回的文件地址写入用户资料
4. 更新到 `member_user.avatar`

因此，微信授权头像这条链路原则上应写入你们自己的文件存储地址，而不是 `pravatar`。

---

## 4. `pravatar` 是从哪里来的

经过代码检索，`https://i.pravatar.cc/300?img=xx` 并不是当前正式分身逻辑中的配置项，而主要出现在测试/造数文件中，例如：

- `docs/s2/gen_match_data.py`
- `docs/s2/seed_match_results.sql`

这些文件会直接把 `pravatar` 写入 `member_user.avatar`，用于演示数据或补测试数据。

所以需要明确区分：

### 正式业务设计

- 创建分身时从 `member_avatars` 表随机取头像

### 历史测试/造数行为

- 脚本或 SQL 直接把 `https://i.pravatar.cc/300?img=xx` 写入 `member_user.avatar`

也就是说，数据库里现在看到的 `pravatar`，大概率是历史测试数据或造数留下来的结果，不代表当前正式逻辑的真实配置。

---

## 5. 为什么会出现“浏览器能看，服务端探测异常”

排查时发现，部分 `pravatar` 链接在浏览器中可以打开，但服务端通过 `HEAD` 请求检查时会返回 `403`。

这说明：

- 该站点可能限制了某些请求方式
- 浏览器直接访问与服务端探测访问并不完全一致

因此不能简单得出“所有 `pravatar` 都彻底失效”的结论。

但可以确认的是：

1. `pravatar` 是第三方外部源，不受项目控制
2. 即使当前部分可访问，也存在未来变更、限流、拒绝访问的风险
3. 它不是项目当前应依赖的正式头像配置源

所以从工程稳定性看，`pravatar` 不适合作为正式生产头像池。

---

## 6. 当前问题总结

当前头像体系主要有以下问题：

### 6.1 正式头像池为空

`member_avatars` 已空，导致：

- 新分身无法从正式头像池中随机到头像
- `/member/user/avatar/random` 接口失去意义

### 6.2 数据库存量头像来源不统一

`member_user.avatar` 中混有：

- 第三方头像源
- 微信头像源
- 测试域名
- 可能的历史文件地址

这会带来：

- 可用性不稳定
- 维护困难
- 无法保证风格统一

### 6.3 前端展示逻辑不一致

部分页面：

- 直接使用前端本地静态图

部分页面：

- 使用数据库头像
- 为空时再兜底

这会导致不同页面的头像表现不一致。

---

## 7. 推荐方案

### 7.1 推荐采用“预生成头像池 + 随机分配”

如果后续要做随机头像，建议采用下面的方案：

1. 先提前生成一批头像图片
2. 上传到你们自己的文件存储/CDN
3. 将头像 URL 写入 `member_avatars.image_url`
4. 创建分身时后端随机选一条写入 `member_user.avatar`

这与当前代码结构完全兼容，改造成本最低。

优点：

- 实现简单
- 成本低
- 稳定性高
- 不依赖第三方随机头像站点
- 易于统一视觉风格
- 与当前后端代码天然匹配

不足：

- 个性化有限
- 用户之间会有一定重复率

但对当前阶段项目，这是最合适的方案。

### 7.2 不建议直接依赖第三方头像站

不建议将以下方式作为正式生产方案：

- 直接依赖 `pravatar`
- 依赖测试域名图片
- 使用不可控外链作为长期头像池

原因：

- 可用性不可控
- 可能被限制访问
- 无法保证商用与版权边界
- 风格不可控
- 后续迁移成本高

### 7.3 实时 AI 生成不建议作为第一阶段方案

理论上也可以在用户创建分身时实时调用 AI 生成头像，但当前不建议优先上这个方案。

原因：

- 接口成本更高
- 生成时间更长
- 失败率更高
- 审核与内容风控更复杂
- 技术链路更重

更合适的顺序是：

1. 先做预生成头像池
2. 业务稳定后，再评估是否引入实时生成

---

## 8. 头像应该上传到哪里

建议所有正式头像都上传到项目现有的文件存储体系，而不是直接放在第三方外链里。

当前项目已经具备统一文件上传能力：

- 后端接口：`/infra/file/upload`
- 配置表：`infra_file_config`
- 后台菜单：`基础设施 -> 文件配置`
- 底层支持：S3 协议对象存储、MinIO、本地、FTP、SFTP 等

也就是说，头像资源建议统一进入：

1. 你们自己的对象存储桶
2. 由 `infra_file_config` 配置为当前主存储
3. 上传完成后拿到可访问 URL
4. 再把该 URL 写入 `member_avatars.image_url`

不要继续依赖：

- `pravatar`
- `test.yudao.iocoder.cn`
- 临时图床
- 不可控的外部 CDN

---

## 9. 推荐使用什么存储

当前项目最适合的正式存储类型是：

- S3 协议对象存储

项目现有代码已经直接支持以下方案：

- 阿里云 OSS
- 腾讯云 COS
- 七牛云
- 华为云 OBS
- 火山引擎 TOS
- MinIO

### 9.1 生产环境推荐

优先推荐：

1. 阿里云 OSS
2. 腾讯云 COS
3. 华为云 OBS

原因：

- 稳定
- 公网访问成熟
- CDN 配套完善
- 非常适合图片类静态资源

### 9.2 测试或内网环境推荐

优先推荐：

1. MinIO

原因：

- 自建方便
- 成本低
- 与项目现有 S3 适配良好
- 适合开发联调和测试环境

### 9.3 选择建议

如果是正式线上业务，建议直接上云厂商对象存储。

如果只是本地联调或测试环境，可以先用 MinIO。

---

## 10. OSS / 对象存储怎么配置

当前项目不是把对象存储写死在代码里，而是走后台配置表：

- 表名：`infra_file_config`
- 后台菜单：`基础设施 -> 文件配置`

配置完成后，项目的 `/infra/file/upload` 就会自动把文件上传到当前主存储。

### 10.1 推荐配置字段

如果使用 S3 协议对象存储，核心配置一般包括：

- `endpoint`：存储服务地址
- `domain`：自定义访问域名或 CDN 域名
- `bucket`：桶名
- `accessKey`
- `accessSecret`
- `enablePathStyleAccess`
- `enablePublicAccess`
- `region`：部分存储可选

### 10.2 建议值

- 头像资源建议使用公开可访问桶
- `enablePublicAccess` 建议为 `true`
- `domain` 建议填写你们自己的 CDN 域名，而不是默认源站地址

如果没有 CDN，至少也要保证：

- 上传后的 URL 能被小程序和 H5 正常访问
- 域名已在对应前端环境白名单中配置

### 10.3 配置来源说明

根据当前项目代码，S3 配置能力已经支持：

- `endpoint`
- `domain`
- `bucket`
- `accessKey`
- `accessSecret`
- `enablePathStyleAccess`
- `enablePublicAccess`
- `region`

所以不需要额外开发新的存储适配器，直接用现有文件配置体系即可。

## 11. 头像文件建议放在哪个目录

建议给头像单独建目录，避免和其它业务文件混在一起。

推荐目录示例：

- `avatar/member/`
- `avatar/preset/`
- `avatar/clone/`

如果当前目标是“预生成头像池”，推荐使用：

- `avatar/preset/`

这样后续管理 `member_avatars` 时最清晰。

---

## 12. 推荐的 Bucket 规划

建议至少满足以下要求：

- 桶中头像资源可公网读取
- 桶开启防盗链或 CDN 策略时，不影响小程序访问
- 文件类型允许图片上传
- 访问域名稳定，不要使用临时测试域名

建议命名示例：

- `eto-avatar`
- `eto-public-assets`
- `eto-static`

如果你们已经有统一静态资源桶，也可以直接复用，不一定单独开新桶。

核心原则是：

- 地址稳定
- 归你们控制
- 对小程序可访问

---

## 13. 推荐的实际落地流程

建议按以下顺序执行：

1. 在对象存储中创建一个公开读取的 Bucket
2. 给这个 Bucket 配置自定义域名或 CDN 域名
3. 在项目后台 `文件配置` 中新增一条 S3 存储配置
4. 将该配置设为主配置 `master`
5. 通过 `/infra/file/upload` 或后台文件上传，把头像上传到 `avatar/preset/`
6. 拿到上传后的 URL
7. 将这些 URL 写入 `member_avatars.image_url`
8. 验证创建分身是否会随机写入 `member_user.avatar`

---

## 14. 是否需要单独开发上传逻辑

一般不需要新开发一套头像上传系统。

因为当前项目已经有：

- 后端文件上传接口 `/infra/file/upload`
- 文件配置能力 `infra_file_config`
- 前端上传逻辑示例

所以实际只需要：

1. 配好对象存储
2. 把头像素材上传进去
3. 把 URL 写进 `member_avatars`

即可完成第一阶段落地。

## 15. 未来落地建议

### 15.1 第一阶段：恢复可用头像池

建议先完成以下事项：

1. 准备一批头像素材，建议 `20-50` 张起步
2. 尺寸统一，例如 `512x512`
3. 上传到你们自己的对象存储
4. 推荐放在 `avatar/preset/`
5. 将 URL 写入 `member_avatars`
6. 验证创建分身时是否能正常随机写入 `member_user.avatar`

建议 SQL 结构保持不变，仅补数据即可。

### 15.2 第二阶段：修复历史坏链

建议排查并处理现有 `member_user.avatar` 中的历史外链数据：

- 对明显失效的 URL 进行替换
- 或统一切换到新头像池中的可控地址

这一步可以通过 SQL 批量处理，也可以通过脚本迁移。

### 15.3 第三阶段：前端加强兜底

建议前端除了“空值兜底”外，再增加“加载失败兜底”：

- 当头像 URL 存在但图片加载失败时，自动回退到 `/static/style_3d.jpg`

这样可以避免坏链直接导致页面裂图。

### 15.4 第四阶段：再评估个性化生成

等头像池和基础展示逻辑稳定后，再考虑：

- 让用户从头像池中手动挑选
- 按性别/风格/标签分组随机
- 接入 AI 批量生成更多统一风格头像
- 按用户资料生成个性化头像

## 16. 推荐实施方式

从当前代码结构和数据库状态出发，推荐的最小可行方案如下：

### 第一步

恢复 `member_avatars` 表数据

### 第二步

所有头像资源迁移到你们自己可控的存储地址

推荐做法：

- 存到 `infra_file_config` 配置的主对象存储中
- 优先使用阿里云 OSS / 腾讯云 COS / 华为云 OBS
- 测试环境可用 MinIO
- 目录建议为 `avatar/preset/`

### 第三步

继续沿用现有后端逻辑：

- `createClone()` 随机取 `member_avatars`
- 写入 `member_user.avatar`

### 第四步

前端增加图片加载失败兜底

这样可以在不重构整体架构的前提下，快速把头像系统恢复到可用、稳定、可维护的状态。

---

## 17. 最终结论

当前项目的正式设计并不是“实时随机生成一个头像 URL”，而是：

**提前准备一批头像 -> 上传到你们自己的对象存储 -> 写入 `member_avatars` -> 创建分身时随机挑一条 -> 写入 `member_user.avatar`**

`pravatar` 出现在数据库中，主要是历史测试/造数行为留下来的结果，不应视为当前正式配置来源。

如果后续要做随机头像，建议继续沿用并完善“预生成头像池 + 随机分配”的模式，并将头像统一托管到项目现有文件存储体系，而不是依赖第三方外链。
